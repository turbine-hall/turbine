## Known limitations

- Local approvals are **local attestations**, not authenticated identity. The terminal + hash check and the Cursor hook are speed bumps: an agent with unrestricted shell access could still drive a pseudo-terminal. For code review and acceptance, `humanGates.requirePrApproval: true` adds a GitHub PR approval that an agent account cannot self-grant.
- Autonomous lane parts A, B, C and G are implemented. Revert detection after a recorded merge, stacked PRs, the sandboxed executor and fleet scheduler remain unimplemented. Source labels are recorded from Jira intake (and the engine `createTask` API); GitHub issue intake does not read labels yet, so `labels`-restricted policies do not match those tasks.
- Projects initialised before this change keep their old `.cursor/hooks/turbine-guard.mjs`; re-run `turbine init` to add the `policy approve|resume` and `task lane --retry` blocks.
- Verification needs `quality.checks` (and usually `quality.setup`, e.g. `npm ci`) in `.turbine/project.yaml`; checks run without a shell (no pipes/globs).
- Repositories the task changes must be declared before plan approval; changes in undeclared repos are invisible to turbine.
- Execution defaults to **manual-supervised** handoff; worktree is not a security sandbox.
- Non-mock model providers are adapter-shaped; mock is the default offline provider.
- GitHub PR automation, web UI, and multi-tenant service are not implemented. Packet→issue mirroring (#21) posts sticky comments when `issue.comment` is allow-listed and the matching adapter is `enabled` (GitHub also needs `mirrorRepos`); still not `issue.transition` / `issue.edit` by default. Live hosts/tokens come from env only: `GITHUB_TOKEN`/`GH_TOKEN` (+ optional `GITHUB_API_BASE_URL`), `JIRA_SITE_URL`+`JIRA_EMAIL`+`JIRA_API_TOKEN` (repo `project.yaml` apiBaseUrl/siteUrl do not receive those tokens). Mirror jobs are serialized after `render`; `syncFromMarkdown` / `task create` / `approve|reject` await them; STATUS skip/success notes appear on the next render.
- Storage uses Node built-in `node:sqlite` (requires Node 22+).
- Project facts (layer 1): convention counts are textual (comments and strings are not parsed); ESLint / `prettier.config.js` are not evaluated; `yarn.lock` and bun lockfiles are not parsed; the version-range check only decides forms it fully understands (otherwise `unchecked`); `.turbine/context/` and `.turbine/knowledge/` are git-ignored because they cite the commit they were built from (export with `turbine knowledge export` to share).
- Knowledge bundle (OKF #14): the bundle never invents facts; Attested Computation concepts and ingesting foreign OKF bundles are out of scope; task-context-as-OKF is a follow-up; license is omitted unless the repo declares one (never guessed); concept keys that fail path safety are skipped rather than invented.
- Claims / brief (layer 2): the verifier proves what the VERIFIER says, not the free-text `statement`; the brief is rendered from verifier + evidence templates. `calls` matches the callee name as written; no binding is resolved. `absence` supports only `literal` and `import-specifier` byte searches with the stated limits. `config` reads `.json` / `.jsonc` only (strict JSON, as npm reads it, except for `tsconfig.json` and `tsconfig.<name>.json`, the same two forms for `jsconfig`, `.eslintrc.json` and `*.jsonc`, which are read as JSONC; a name such as `tsconfig-base.json` is strict). `dependency` checks the declared version (and optional `usedIn` import), not the installed one. `reverifyOnCommit` is wired into `understand` / brief ensure when the claim frontier is behind HEAD. Drafting uses a capped sample of key files (not the whole tree). Approval is a local attestation (TTY + typed short hash), same class of speed bump as task gates.
- Task context (layer 3): a selection, never a complete list. Source files are parsed with the TypeScript parser (`typescript` is a runtime dependency of the CLI, loaded on the first scan). A file with any syntax error, or nested too deeply for the parser, states nothing (it is counted as not parsed); errors only the type checker finds (`export const x;`) are not detected, because they need a whole-program check; static imports and exports count only at the top level; a `require()` call counts only when `require` is not bound anywhere in the file (a parameter, variable, function or import named `require` may shadow the loader), and the calls left out for that reason are counted in the document, not dropped; `import('x')` written in a type position is not read. Imports are resolved only for relative specifiers and workspace package names. A package with `exports` is resolved the way Node selects a target for the statement's mode, `import` or `require`, which comes from the importing file's format (`require()` is `require`; `.mjs`/`.mts` files and files under a package with `"type": "module"` use `import`; static imports in `.cjs`/`.cts` files use `require`, a dynamic `import()` there stays `import`; any other file is not known and gets an edge only when both modes agree) (checked against Node): the first matching condition in manifest order (`default`, `node`, `node-addons` and the mode apply), falling through to the next key when a nested condition has no answer, `null` blocks, an array uses its first entry that gives a target (a `null` or invalid-target entry is passed over; an invalid configuration such as an array-index key is not) without falling back when that target's file is missing, a map that mixes sub-paths and conditions is invalid, a `module-sync` condition makes the answer ambiguous (it depends on the Node version) so nothing is claimed, and a target must be a `./` path with no `.`, `..` or `node_modules` segment (however percent-escaped) that resolves, as a file URL, to one exact tracked file. `"exports": null` means no exports. Without `exports` only `main`, then `index.js`, are used, looked up in Node's order (`main` as written, `.js`, `.json`, `.node`, then as a directory index; then the package's `index.js/.json/.node`) before the build-output proof and before any TypeScript source is tried: `module`, `types` and `typings` are not what Node loads. A type-only import gets an edge only when both modes agree. An entry that names untracked build output (`./dist/index.js`) maps to its source only when the package's tsconfig (and the configs it `extends`, relative paths only, all read at the commit) proves the emit: `outDir` and `rootDir` set (declaration files go to `declarationDir` when set), no `noEmit`, an output kind the options produce (`.d.ts` needs `declaration` or `composite`; `.mjs`/`.cjs` need `.mts`/`.cts` sources; `emitDeclarationOnly` emits no `.js`), and the source is a compilation input (`files`, or `include` and not `exclude`; the default exclude holds `node_modules`, `outDir` and `declarationDir`; a declaration file is never a source; using the `*`, `?` and `**` syntax only; any other glob syntax, a pattern or path beyond the matcher's work limits, a hidden directory, an absolute path or one leaving the repository, an unreadable or non-relative `extends` leaves it unconfirmed and no edge is stated; the matcher is iterative, not recursive). `tsconfig` `paths`/`baseUrl` aliases, sub-path imports of workspace packages, `node_modules` packages and run-time-computed imports are not resolved, and only JS/TS sources are scanned (the document states how many files were not read or parsed). Manifests, tsconfig files next to a workspace `package.json`, and CODEOWNERS share a 16 MiB budget (1 MiB per file); what it leaves out is counted in the document. CODEOWNERS rules are matched by an iterative matcher (no regular expressions; a rule beyond the work limits is skipped and counted), a `**` between directories matches zero or more of them, and the verifier checks the recorded owners against the active CODEOWNERS file. The related-test limit counts distinct test files. The nearest tracked `package.json` gives the importing file's `"type"` (an unreadable one gives no type); every tracked `package.json`, `tsconfig*.json` and CODEOWNERS is read under the metadata budget, nearest the root first, so a config extended from outside the workspace roots is available; a native `import()` in a `.js`/`.jsx` file uses the `import` condition. A CODEOWNERS rule skipped (not modelled, or beyond the work limits) AFTER the matching rule makes the owner unconfirmed, and a CODEOWNERS reason must carry 0 points. A `.min.js` input found only by a wildcard, and an `extends` target that is tracked but not read, leave the build-output mapping unconfirmed. A CONTEXT.md that is not valid UTF-8 is a read error, never rewritten. `CONTEXT.md` is read through one bounded reader (regular file, 1 MiB; opened without blocking, so a FIFO is refused);: a file that is too large, unreadable or a symlink is reported by lint and stops the render with the file left as it is (agent notes are never replaced by empty notes; only a missing file starts empty), and it is replaced through a temp file and rename. The marker hash covers the snapshot and commit as well as the body; a new document over the size limit is not published (the old file stays); the file is read again right before publishing and rebuilt from the new notes if it changed (the window is narrowed, not closed: there is no cross-process lock); `evidence/context.json` is written first and `CONTEXT.md` last; a render after a state transition records a `context.render-failed` event instead of failing the transition; the CHANGES_REQUESTED event and the state are saved in one transaction that re-reads the stored state; the `repo-context` record and its `context.selected` event are saved in one transaction; `evidence/context.json` carries the hash of the `CONTEXT.md` published with it (`document`); a write failure is `E_CONTEXT_UNAVAILABLE`; a plan whose HEAD moved while the model ran is discarded (retry with `sync`); the budget provenance (declaring roles) is part of staleness; `outFile`/`out`, an `extends` that cannot be read exactly (the exact path first, then `.json`) and declaration inputs leave the build-output mapping unconfirmed. The roles are chosen by the assessment itself, so the selection that goes into the assess prompt uses the default size limit; a role `context_budget` takes effect from the next rebuild (`budget-changed`). Only the CHANGES_REQUESTED entries made through the engine are counted for the rebuild rule.
